# Accessibility

Every component in this registry targets **WCAG 2.2 level AA**: usable with a keyboard, understandable with a screen reader, and readable for people with low vision or colour blindness.

> This page describes how the components are built and tested. It isn't a conformance claim for any product. Each product team is responsible for testing its own pages, content and flows.

Automated tools find roughly a third of accessibility problems. The rest needs people:

- **Keyboard check:** use the component with the keyboard only. Is the order logical? Is focus always visible?
- **Screen reader check:** try it with NVDA (Windows) or VoiceOver (macOS). Is everything announced clearly and in a sensible order?
- **Zoom check:** at 200% browser zoom and at phone width, does anything overlap or get cut off?

## Using components accessibly

Components can only do so much; how they're used matters as much.

- **Label everything.** Every input needs a visible label; icon-only buttons need an `aria-label`.
- **Write clear text.** Button labels say what happens ("Save changes"); error messages say how to fix the problem.
- **Use headings in order** on your pages, so screen-reader users can navigate by them.
- **Don't override focus styles** or remove the focus ring.
- **Use the right component for the job:** a link to navigate, a button to act.

Each component's Docs page has its own **Accessibility** section with specific guidance.

## Reporting a problem

Open an issue in the ui-registry repository with the label `accessibility`. Include the component, the story, what you expected, and what happened (with the browser and assistive technology used).
